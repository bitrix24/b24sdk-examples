# Task Planner

## Workflow

Следовать этому workflow последовательно. Не считать работу завершённой, пока план не сохранён в `.tasks/` и не прошёл повторную проверку.

1. Если задача не сформулирована явно, задать один короткий вопрос: `Что нужно сделать?`
2. Прочитать [`AGENTS.md`](../../../AGENTS.md) и затем только релевантные артефакты проекта.
3. Собрать минимальный контекст для планирования: затронутые файлы, ограничения архитектуры, команды `make`, существующие планы в `.tasks/`.
4. Составить рабочий план по шаблону из [`references/plan-template.md`](references/plan-template.md).
5. Сохранить план в `.tasks/<slug>-plan.md`, где `<slug>` коротко описывает задачу.
6. Переоткрыть сохранённый файл и проверить его по [`references/plan-review-rubric.md`](references/plan-review-rubric.md).
7. Если найдены неоднозначности, архитектурные конфликты или лакуны, исправить план и повторить проверку.
8. В сообщении пользователю указать путь к сохранённому плану и перечислить оставшиеся assumptions или риски.

## Что читать перед планированием

Читать только нужное для конкретной задачи, но не пропускать обязательные источники истины:

- Всегда читать [`AGENTS.md`](../../../AGENTS.md).
- Читать [`Makefile`](../../../Makefile), если план затрагивает команды, тесты, локальное окружение или новые операционные шаги.
- Читать [`README.md`](../../../README.md), если задача меняет пользовательский или девелоперский сценарий.
- Читать [`config/services.yaml`](../../../config/services.yaml), если задача затрагивает DI, handlers или wiring.
- Читать существующие файлы в `.tasks/`, если нужен пример структуры или ранее зафиксированные assumptions.
- Дочитывать конкретные файлы из `src/`, `public/`, `bin/` только для затронутой области.

## Правила плана

- Писать план в терминах наблюдаемых изменений: файл, действие, ожидаемый результат, способ проверки.
- Не оставлять расплывчатые формулировки без явного assumptions.
- Учитывать проектные ограничения из `AGENTS.md`:
  - все операционные действия только через `make`;
  - после реализации обязателен `make test`;
  - связанные чеклисты нужно обновлять;
  - нельзя предлагать изменения, которые противоречат текущей доменной разбивке без явного шага по рефакторингу.
- Если для операции нет make-target, сначала добавить target в [`Makefile`](../../../Makefile), а уже потом ссылаться на него в плане.

## Проверка после сохранения

После записи файла в `.tasks/` обязательно выполнить три проверки:

1. Проверить однозначность: сможет ли другой исполнитель пройти по шагам без скрытых догадок.
2. Проверить архитектурную совместимость: нет ли конфликта с `AGENTS.md`, `Makefile`, DI и текущей структурой каталогов.
3. Проверить лакуны: не пропущены ли тесты, конфиг, документация, миграции, регистрация сервисов, зависимости, чеклисты.

Не оставлять результат в статусе `почти готово`. Если обнаружен пробел, исправлять сам план и документировать результат в секции `Review Notes`.
