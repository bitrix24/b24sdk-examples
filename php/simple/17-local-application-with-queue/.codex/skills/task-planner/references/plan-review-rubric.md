# Рубрика проверки плана

Использовать эту рубрику после сохранения файла в `.tasks/`. Если проверка не пройдена, сначала исправлять сам план, и только потом считать работу завершённой.

## 1. Проверка на однозначность

Проверять каждый пункт плана по вопросам:

- Понятно ли, какой именно результат должен получить исполнитель?
- Понятно ли, в каких файлах или подсистемах ожидаются изменения?
- Понятно ли, как будет проверяться результат?
- Есть ли слова вроде `при необходимости`, `где-то`, `что-нибудь`, `и так далее`, которые скрывают незавершённое решение?

Если ответ `нет`, переписывать пункт в наблюдаемой форме: файл, действие, результат, способ проверки.

## 2. Проверка на соответствие архитектуре проекта

Сверяться минимум с этими артефактами:

- `AGENTS.md`
- `Makefile`
- `README.md`, если затрагивается пользовательский или операционный сценарий
- `config/services.yaml`, если меняются wiring, DI, handlers
- релевантные файлы в `src/`, если план затрагивает доменные границы

Отдельно проверять:

- не предлагает ли план обходить правило `все операции только через make`;
- сохраняет ли план текущую доменную разбивку проекта;
- не требует ли план несуществующих entrypoint/command без явного шага по их добавлению;
- не игнорирует ли обязательный `make test`.

## 3. Проверка на лакуны

Искать пропуски по категориям:

- конфигурация и env-переменные;
- DI / регистрация сервисов / автоконфигурация;
- тесты и quality gates;
- документация и примеры использования;
- миграции данных или совместимость со старым поведением;
- внешние зависимости и ограничения окружения;
- связанные чеклисты.

Если категория не относится к задаче, отметить это явно в `Review Notes`, а не молча пропускать.

## 4. Критерий готовности

Считать план готовым только если одновременно выполнены условия:

- файл сохранён в `.tasks/`;
- все спорные места либо устранены, либо оформлены как явные assumptions;
- нет конфликта с текущей архитектурой;
- нет незакрытых лакун без пояснения.
